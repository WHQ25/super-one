## 它做什么

ACP agent 的工具调用渲染进其他每个 harness 共用的那套聊天界面 —— 读就是读,编辑显示 diff,搜索显示它的查询词。

## 怎么工作

ACP 用一个 `kind`(`read`、`edit`、`execute`、`search`、`fetch`、`delete`、`think`)加上形状由 agent 自定的原始参数来描述一次工具调用。归一化把两者都用上:

- 当 agent 给出了有意义的 `kind`,就信任它,并据此渲染该行。
- 然后在原始参数里探测这一行真正需要的字段 —— 路径、模式、查询词、URL —— 并覆盖不同 agent 对同一件事所用的多个名字。
- 带查询词而没有 URL 的 `search` 是网页搜索;同样形状带上 URL 就是 fetch。这个消歧是在参数上做的,不是在工具名上做的。
- 那些无论怎么拼写都明显是 grep 的名字(`grep`、`Grep`、`ripgrep`、`code_search` 等)收敛到同一种行类型。

## 为什么要归一化而不是直接透传

ACP 对参数形状是有意放松的,这正是任何 agent 都能讲它的原因。代价是:一个透传的渲染器会为六个 agent 做同一件读文件的事,显示出六种长得不一样的行。归一化就是这份松散被吸收掉的地方 —— 只吸收一次,而不是渗进界面里每一个想知道「这次调用做了什么」的角落。

## 常见问题

**归一化器不认识的工具会怎样?** 它渲染成带参数的通用工具行 —— 不会丢东西。
